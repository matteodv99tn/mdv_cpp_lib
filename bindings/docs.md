# Binding Generation (Developer Guide)

We use [SWIG](https://www.swig.org/) (_Simplified Wrapper Interface Generator_) to generate language bindings.
As of now, the only supported language is Python.

This doc focuses on developers working on bindings from source. It explains how the
bindings are generated, how to add new modules, and how to keep the Python wrappers
clean, typed, and documented.

## Build entry points

Bindings are built by CMake when `BUILD_BINDINGS=ON` is set in the top-level
`CMakeLists.txt`. The bindings-specific configuration lives in `bindings/CMakeLists.txt`.

Quick path for developers (recommended):

```bash
# one-time editable install
pip install -e .

# configure a bindings-only build and install into your active python site-packages
CMAKE_INSTALL_MODE=ABS_SYMLINK \
  cmake -B build \
  -DBUILD_BINDINGS=ON \
  -DCMAKE_INSTALL_PREFIX=$(python -c "import sysconfig; print(sysconfig.get_paths()['purelib'])")

# build + install
CMAKE_INSTALL_MODE=ABS_SYMLINK cmake --build build --parallel
CMAKE_INSTALL_MODE=ABS_SYMLINK cmake --install build
```

Notes:
- `CMAKE_INSTALL_MODE=ABS_SYMLINK` creates symlink installs, so edits in
  `bindings/python/` show up immediately in `site-packages` and still track in git.
- `pip install -e .` triggers a full build; run it once to set up dependencies,
  then use the CMake commands above for iterative work.

## Repository layout

```
bindings/
  CMakeLists.txt              # SWIG build rules
  swig/                       # SWIG interface files
    eigen.i                   # vendored (not authored here)
    numpy.i                   # vendored (not authored here)
    mesh.i                    # mdv::mesh bindings
  python/                     # public Python package (typed, documented)
    __init__.py
    mesh/
      __init__.py
      _mesh_impl.py            # generated by SWIG at build time
      mesh.py                  # typed wrapper around _mesh_impl
      ...
```

## How SWIG is configured

`bindings/CMakeLists.txt` defines a helper function `swig_lib_module_wrapper()`.
It sets the SWIG module name to `_MODULE_impl` and builds a shared library named
`libMODULE`. For `mesh`:

```
swig_lib_module_wrapper(mesh SOURCES swig/mesh.i)
```

Build outputs of SWIG for Python:
- `_mesh_impl.py` (pure Python API generated by SWIG)
- `_libmesh.so` (compiled extension loaded by `_mesh_impl.py`)

Install destinations:
- `_mesh_impl.py` is installed into `mdv/mesh/`
- `libmesh` is installed into `mdv/mesh/` and loaded by `_mesh_impl.py`
- The public Python wrappers are installed from `bindings/python/` into `mdv/`

## Python wrapper strategy

SWIG output lacks proper type hints and rich docs, so the generated module is
treated as a private implementation.

Convention:
- The SWIG-generated Python module is `_MODULE_impl.py`
- The public module is `bindings/python/MODULE/*.py`
- Public modules wrap `_MODULE_impl` and add:
  - numpy-style docstrings
  - type hints
  - more Pythonic APIs if needed

Example (from `bindings/python/mesh/mesh.py`):

```python
from ._mesh_impl import Mesh as _MeshImpl

class Mesh:
    def __init__(self, mesh_impl: _MeshImpl | None = None):
        if mesh_impl is not None:
            self._mesh_impl = mesh_impl
            return
        ...
```

## Adding a new binding module

1) Create a new SWIG interface file

- Add `bindings/swig/<module>.i`
- Follow the existing pattern in `bindings/swig/mesh.i`
- Include headers inside `%{ %}` and add public declarations under the
  namespace you are binding.

Minimal skeleton:

```
%module my_module

%{
#include "mdv/my_module/foo.hpp"
%}

%include "std_string.i"
%include "std_vector.i"
%include "eigen.i"

%eigen_typemaps(Eigen::Vector3d)

namespace mdv::my_module {
    class Foo {
    public:
        Foo();
        double value() const;
    };
}
```

2) Register the module in `bindings/CMakeLists.txt`

```
swig_lib_module_wrapper(my_module SOURCES swig/my_module.i)
```

3) Add the Python wrapper package

- Create `bindings/python/my_module/__init__.py`
- Add public wrapper(s) that import `_my_module_impl` and add types/docstrings

Example `__init__.py`:

```python
from .foo import Foo

__all__ = ["Foo"]
```

4) Build and verify import

```bash
cmake -B build -DBUILD_BINDINGS=ON
cmake --build build --parallel
cmake --install build

python -c "import mdv.my_module as mm; print(mm.Foo().value())"
```

## SWIG authoring guidelines (repo-specific)

- Prefer explicit declarations in the `.i` file rather than `%include`-ing many
  headers; this keeps the Python surface stable and intentional.
- Use `eigen.i` typemaps for Eigen types used in public APIs:
  `Vector2d`, `Vector3d`, `VectorXd`, `MatrixXd`, `MatrixXi`.
- Any factory or function returning a new heap object should be annotated with
  `%newobject` to transfer ownership to Python.
  Example (from `mesh.i`):
  - `%newobject mdv::mesh::load_from_file;`
  - `%newobject mdv::mesh::extract_normal_bounded_surface;`
- When returning values that need custom conversion, use typemaps. The mesh
  bindings include a typemap for `mdv::mesh::Mesh` to ensure correct ownership:

```
%typemap(out) mdv::mesh::Mesh {
    $result = SWIG_NewPointerObj((new $1_ltype(std::move($1))),
                                 $&1_descriptor, SWIG_POINTER_OWN);
}
```

## Python API guidelines

- Public modules should be small, typed wrappers around `_MODULE_impl`.
- Use numpy-style docstrings for every public class/function.
- Keep generated `_MODULE_impl.py` untouched; only edit files in
  `bindings/python/`.
- If you add new SWIG-exposed symbols, mirror them in the Python wrappers and
  keep the public API stable.
- Normalize vector outputs from SWIG to 1D numpy arrays
  (e.g., use `np.asarray(x).reshape(-1)` for 3x1 vectors).
- Validate array-like inputs at the Python boundary with `np.asarray(...)` and
  explicit shape checks. Prefer the helpers in `bindings/python/mesh/_validation.py`.
- Prefer explicit constructors (`from_*`/`@classmethod`) for multi-input objects.
  Keep `__init__` minimal and document alternative constructors.
- Maintain `.pyi` stubs alongside the wrappers for clear signatures and IDE
  support. Keep them in sync with runtime behavior.

## Debugging and troubleshooting

- If import fails, verify that both `_MODULE_impl.py` and `_libMODULE.so` are in
  the same package directory under `site-packages/mdv/<module>/`.
- Rebuild after any change to `.i` files; they regenerate `_MODULE_impl.py` and
  the wrapper C++.
- If you changed Eigen signatures, ensure the matching `%eigen_typemaps()` are
  present in the `.i` file.
- If ownership bugs appear (double free / leaks), double check `%newobject` and
  `typemap(out)` rules.
